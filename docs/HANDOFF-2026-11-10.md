# quick-imposing 핸드오프 (2026-11-10, 2026-11-11 갱신)

## 목표와 범위

**프로젝트 목표**
베이스 PDF 위에 카드 PDF(B)를 정해진 셀에 배치해서 인쇄용 판(하리꼬미) PDF 한 장을 만드는 도구를 만든다.
- A와 B의 벡터 특성(패스, 폰트, 이미지, 색 공간, 투명도, 오버프린트, 레이어)을 변형하지 않는다.
- 쿽(QuarkXPress)으로 하던 임포징을, 그래픽 툴에 미숙한 인쇄 실무자도 할 수 있게 하는 것이 컨셉이다.
- 최종 형태는 Windows용 GUI 프로그램 두 개다. 템플릿 편집기와 작업 프로그램이다.

**현재 단계**
- 기술 검토, 1·2차 테스트 명세, 2차 구현 PR 검토, 템플릿·프로젝트 요구사항 정리까지 끝났다.
- 다음 단계는 기능 테스트 보강이다. 배치 기능 검증이 아직 충분하지 않으므로, 화면(UI) 구성 정리는 기능 테스트를 충분히 한 뒤의 과제로 미룬다.

**작업 분담**
- 구현은 Codex(코딩 에이전트)가 저장소 문서를 기준으로 수행한다.
- 이 핸드오프를 받는 쪽의 역할은 기획, 분석, 설계, 문서 작업, 리뷰다.

## 제약과 선호

- **작업 범위**: 기획·분석·설계·글쓰기·문서·관리·리뷰. 코드 작성과 수정은 명시적인 지시가 없으면 하지 않는다. 테스트 템플릿 JSON이나 기대값 같은 데이터 파일 작성은 수행한 적이 있다.
- **언어**: 한국어
- **문서 반영**: 저장소 `docs/`에 Markdown으로 올리고 `main`에 직접 커밋한다.
  - 커밋 작성자: `steves460ng <steves460ng@users.noreply.github.com>`
- **저장소 공개 범위**: 저장소는 public이다. 샘플 PDF도 공개 상태다. 실제 데이터를 쓸 때는 private 전환을 권고한 바 있으며, 아직 결정되지 않았다.
- **기준 수치**: 실측값을 우선한다. 설계 문서에 쓰는 값은 파일에서 직접 확인한다.

## 확정된 결정

### 배치·비변형 규칙

기준 문서는 `docs/SPEC.md` v0.5다.

- **B 가공 순서**: B를 회전한 뒤 중앙 기준으로 클리핑한다.
  - 클리핑은 객체를 삭제하지 않는다. Form XObject의 `/BBox` 등으로 가린다.
  - 배치는 회전과 이동 행렬만 쓴다. 배율 변경은 금지한다.
- **원본 보존**: B의 콘텐츠 스트림은 디코딩 후 바이트가 원본과 같아야 한다. 이미지와 폰트 스트림은 원본 바이트 그대로 둔다. 베이스 콘텐츠는 변경하지 않고, 배치 명령을 뒤에 추가하는 방식만 쓴다.
- **보존 항목**: B 페이지의 투명도 그룹을 유지한다. OCG(레이어)를 결과 문서에 등록하고 기본 ON으로 둔다. 색 공간과 오버프린트도 보존한다.
- **금지 사항**: Ghostscript 같은 재해석 도구로 결과를 생성하지 않는다.
- **R11 (필수)**: 결과를 저장하기 전에 카탈로그와 페이지의 `/PieceInfo/Illustrator`만 삭제한다.
  - 이유: Illustrator가 PDF 콘텐츠 대신 이 전용 데이터를 열어서 카드가 안 보이는 문제가 있었다.
  - 결과: PR #1 결과물을 Illustrator에서 직접 열어 해결을 확인했다(사용자 수동 확인).
- **NC 재단 여유**: B는 이후 NC 재단 여유까지 고려해 디자인된다. 따라서 도구는 도련 추가나 크기 보정을 하지 않는다.
- **입력 파일 전제**: 실제 작업에서 B는 폰트를 모두 윤곽선 처리한 상태로 넘어온다.

### 템플릿·프로젝트 요구사항

기준 문서는 `docs/TEMPLATE-REQUIREMENTS.md` v0.3이다.

**프로그램과 사용자**
- 템플릿 편집기와 작업 프로그램은 별도 프로그램이다. 운영 환경은 Windows다.
- 템플릿은 설치 시 만들어지는 별도 폴더에 두고, 공유하지 않는다.
- 사용자는 그래픽 툴에 미숙한 인쇄 실무자다. mm 좌표계(대지 좌상단 원점)에 익숙하고, 프로그래밍 지식은 없다.

**템플릿 구성**
- 템플릿 1개 = 폴더 1개다. 폴더에는 템플릿 정의와 베이스 PDF 사본이 들어간다.
- 템플릿은 판 구조만 담는다. 데이터 배정은 프로젝트에 담는다.
- 템플릿 이름은 작업자가 정한다(예: `BC-COMBI-전면`). 문제가 되는 특수문자만 금지한다.
- 전면과 후면은 별개 작업이고, 템플릿도 따로 만든다. 템플릿마다 다른 베이스를 쓸 수 있다.

**셀 배열과 B 가공**
- 셀 배열은 다음 값으로 자동 생성한다.
  - 첫 셀 좌상단 위치(mm)
  - 가로·세로 셀 개수
  - 가로·세로 피치. 피치는 셀 시작점에서 다음 셀 시작점까지의 거리다(예: 85 + 1 = 86).
  - 셀 크기. 템플릿마다 다르며, 재단까지 고려한 크기다.
- 자동 생성된 셀은 개별로 옮기거나 삭제하지 않는다.
- 회전은 0°, 90°, −90°, 180° 중 하나다.
- 클리핑 크기는 항상 셀 크기와 같다. B는 셀 중심에 맞춰 정렬한다.

**텍스트 항목**
- 템플릿에는 위치(mm), 글꼴(시스템 글꼴), 크기만 정의한다. 내용은 작업할 때 입력하며, 빈 값도 허용한다.
- 색은 K100 고정이고 CMYK 색 공간을 쓴다. 윤곽선 처리는 하지 않는다.
- 베이스는 바뀌는 텍스트(제품명, 날짜, 작업 팀명)를 지운 "빈 베이스"로 준비한다.

**프로젝트**
- 프로젝트는 임포징 PDF와 같은 위치에 저장하며, 저장 위치는 사용자가 정한다.
- B는 프로젝트 파일 기준 상대경로로 참조한다.
- 겹친 데이터는 나중에 넣은 것이 위에 그려진다.
- 데이터를 교체할 때는 셀의 기존 데이터를 지우고 다시 불러온다. 겹침 순서는 원래 순서를 유지한다.
- 데이터가 셀 수보다 많으면 템플릿을 다시 열어 남은 데이터로 새 프로젝트를 작업한다.

**자동 배열** (`docs/TEMPLATE-REQUIREMENTS.md` §6.4)
- 셀 번호는 좌상단부터 행 우선(→ 다음 ↓)으로 매기는 고정 번호다.
- 작업자가 셀 하나를 선택하고 B 파일을 여러 개 고르면, 파일을 이름순으로 정렬해 선택한 셀부터 차례로 넣는다.
  - 숫자는 크기대로 비교한다(`B-2` → `B-10`, Windows 탐색기 방식).
  - 이 정렬 순서가 곧 넣은 순서이며, 겹침 순서도 이를 따른다.
- 채움 방향은 템플릿마다 정한다. 작업할 때는 바꾸지 않는다.
  - 정방향: 각 행을 왼쪽 → 오른쪽으로 채운다.
  - 역방향: 각 행을 오른쪽 → 왼쪽으로 채운다.
  - 행은 어느 방향이든 위 → 아래로 진행한다.
- 3열 판의 전체 순서는 다음과 같다.
  - 정방향: 1, 2, 3, 4, 5, 6, 7, 8, 9
  - 역방향: 3, 2, 1, 6, 5, 4, 9, 8, 7
- 선택한 셀이 첫 파일을 받고, 이후 파일은 전체 순서에서 그 셀 다음부터 이어서 들어간다.
  - 예: 역방향에서 5번 셀을 선택하면 5, 4, 9, 8, 7 순서로 채운다. 6번 셀은 채우지 않는다.
- 배열이 막히면 그 앞까지 넣은 파일은 그대로 두고 멈춘다. 그리고 들어가지 못한 파일을 경고로 알린다.
  - 막히는 경우 1: 남은 셀 수보다 파일이 많을 때
  - 막히는 경우 2: 채울 경로에 이미 데이터가 있는 셀이 있을 때
  - 예: 파일 5개, 남은 셀 3개 → 앞의 3개를 넣고 2개는 넣지 못했다고 경고한다.
  - 경우 2를 경우 1과 같은 방식으로 처리한 것은 경우 1의 결정을 그대로 확장한 것이다. 사용자 확인은 받지 않았다.

**예외 처리**: 작업을 막는 경우는 하나뿐이다.

| 상황 | 동작 |
|---|---|
| 수정된 템플릿에 프로젝트가 쓰던 셀이 없음 | 오류 안내 (유일한 차단 조건) |
| 자동 배열 중 남은 셀 초과, 또는 이미 채워진 셀을 만남 | 그 앞까지 채우고 경고 |
| 셀 겹침 | 경고 후 진행 |
| B 크기가 셀과 다름 | 경고 없이 진행 |
| 셀이 마크 영역에 걸침 | 경고 없이 진행 |
| 셀이 판 바깥으로 나감 | 판 바깥 부분은 잘라냄 |
| 다시 연 프로젝트에서 B 파일이 없음 | 안내 없이 빈칸 |

템플릿을 수정한 뒤 프로젝트를 다시 열면 수정된 템플릿 기준으로 열린다.

## 미결 사항과 차단 요인

1. **UI 구성**: 템플릿 편집기와 작업 프로그램의 화면 구성. 기능 테스트를 충분히 한 뒤 다룬다.
2. **텍스트 입력칸 이름표**: 작업 화면의 텍스트 입력칸에 항목 이름표(예: 제품명)를 표시할지
3. **파일 형식**: 템플릿 폴더 안의 파일 이름, 템플릿·프로젝트 파일의 세부 형식(스키마)과 버전 표기
4. **겹침 경고 시점**: 겹침 경고를 언제, 어디에 표시할지(템플릿 편집 시 또는 작업 시)
5. **기존 문서 개정**: SPEC과 TEST-02 본문을 새 요구사항에 맞게 개정하는 방법(개정 또는 대체 표시)
6. **SPEC 미결 항목**
   - 베이스 실측 높이 506mm와 요청 사양 505mm의 차이
   - 카드별 재단선 필요 여부
   - 인쇄소 요구 PDF 규격(PDF/X 등)
   - 마크와 카드 사이 최소 거리
7. **빈 베이스 샘플**: 빈 베이스 샘플 파일이 아직 없다. 현재 샘플 베이스에는 날짜와 라벨 텍스트가 남아 있다.
8. **저장소 공개 범위**: public 유지 여부

## 다음 작업 (의존 순서)

1. 기능 테스트를 보강한다. 어떤 기능을 어떤 범위로 더 시험할지는 사용자와 정한다. 후보는 다음과 같다.
    - 새 요구사항의 셀 배열 규칙(시작 위치·개수·피치·셀 크기)
    - 겹침 순서(넣은 순서), 판 바깥 잘라냄
    - 베이스 텍스트 삽입(K100, 시스템 글꼴 임베드)
    - 자동 배열: 정방향·역방향, 중간 셀에서 시작, 파일 이름 숫자 정렬, 막힘 처리(남은 셀 초과, 채워진 셀)
2. 기능 테스트에 필요한 형식을 정한다. 템플릿·프로젝트 파일 형식 초안과 SPEC·TEST-02 가운데 대체된 규칙의 개정이 여기에 해당한다(미결 3, 5).
3. 사용자에게 빈 베이스 샘플을 받는다. 테스트 명세, 템플릿·프로젝트 샘플, 기대값을 준비한다(미결 7).
4. 구현은 Codex에 맡기고, 결과 PR을 검토한다.
5. 기능 테스트가 충분해지면 템플릿 편집기와 작업 프로그램의 UI 구성을 요구사항 인터뷰로 정리한다(미결 1, 2, 4).
6. PR #1 브랜치 정리 시점을 사용자와 정한다.

위 목록은 작업 순서 제안이며 실행 승인이 아니다. 저장소 공개 범위 변경, 브랜치 삭제, PR 코멘트 게시 등 외부에 영향을 주는 작업은 사용자 확인 후 진행한다.
