## 목표와 범위

- 두 프로그램(작업 프로그램 `QuickImposing.exe`, 템플릿 편집기 `QuickImposingEditor.exe`)의 화면을 한국어와 영어로 쓸 수 있게 한다.
- 사용 설명서(README, 배포본 `사용설명서.md`)와 배포본의 서드파티 라이선스 안내도 영어판을 둔다.
- 범위 밖:
  - PDF 생성 결과는 바뀌지 않는다(언어와 무관).
  - 명령행 메시지와 리포트(`.report.json`)는 이미 영어 사유 + 오류 코드라 바꾸지 않는다.
  - 내부 문서(SPEC, 작업 지시서, PR 기록)와 `build.ps1`의 안내 문구는 한국어 그대로 둔다.
  - 사용자 입력(템플릿 이름, 텍스트 항목 이름, 메모)은 번역하지 않는다.

## 제약과 선호

- 사용자 기본 선호: 기획 · 분석 · 문서 · 검토. 코드 작성 · 수정은 사용자가 지시할 때만 한다. 답은 한국어로.
- 단계마다 새 브랜치(`claude/<이름>`) → GitHub PR(설명에 기록) → Linux 테스트와 Windows 워크플로 통과 → 사용자 지시가 있으면 병합.
- Windows 워크플로는 `claude/**` 브랜치 push로 돌지 않아 수동 실행(`workflow_dispatch`)한다. 자세한 것은 HANDOFF-2026-11-16 §5.
- 1차 베타(사용자 직접 테스트) 중이다. 화면이 바뀌는 변경은 미리 알리고 합의한다.

## 확정된 결정

- **방식은 A, 언어별 문구 파일**로 한다(2026-11-16 사용자 결정).
  - 모듈 `imposing/i18n.py`와 문구 파일 `imposing/locales/ko.json`, `en.json`.
  - 화면에서 `t("키", 값=...)`로 문구를 꺼낸다.
  - Qt에 의존하지 않게 만들어 화면 없는 계층(`session.py`, `store.py`)에서도 쓴다.
- 다국어 작업은 **기본 기능이 어느 정도 만족스럽게 갖춰진 뒤** 한다. 그때까지는 다른 기능 추가가 먼저다(2026-11-17, 2026-11-19 확인).

## 마친 작업과 근거

구현은 하지 않았다. 검토만 했고, 아래 수치는 main `0df808c`에서 측정한 값이다.

| 영역 | 규모 | 다국어 작업 |
|---|---|---|
| `imposing/gui/work.py` | 한국어 문구 168, 값이 들어가는 문구(f-string) 39 | 번역 대상(가장 큼) |
| `imposing/gui/editor.py` | 92 + 14 | 번역 대상 |
| `imposing/gui/common.py` | 14 + 3 | 번역 대상 |
| `imposing/session.py`, `store.py` | `SessionError` · `TemplateError`로 한국어 문장을 만드는 곳 약 24곳 | 문장 대신 코드와 값을 넘기고, 화면이 `t()`로 문장을 만든다 |
| 조사 처리(`을(를)`, `(으)로` 등) | `work.py` 6곳, `editor.py` 1곳 | 문장 전체를 이름 붙은 값 자리(`{name}`, `{count}`)가 있는 틀로 |
| 파일 고르기 창 형식 이름 `"PDF 파일 (*.pdf)"` | 3곳 | 번역 대상 |
| Qt 기본 대화상자 버튼 | 지금 "OK" 등 영어로 나와 한국어 화면과 섞임 | Qt 번역 파일(`qtbase_ko.qm`)을 불러오면 해결 |
| 테스트 | 한국어 문구를 직접 확인하는 줄 약 66개 | 문구가 아닌 키로 확인하거나, 한국어로 고정해 실행 |
| 엔진 · 자동 배열 · 명령행 · 리포트 | 영어 사유 + 오류 코드(리팩토링 R1 · R5 결과) | 변경 없음 |

그 밖에 확인한 것:
- 설치된 PySide6 6.10.1(Linux)에 `lupdate` · `lrelease` 도구와 Qt 번역 파일 32개(`qtbase_ko.qm` 포함)가 있다.
- Windows 배포본(PyInstaller)에 Qt 번역 파일이 들어가는지는 **확인하지 않았다.** 1단계에서 확인한다.
- 지금 코드에는 언어 · 번역 처리가 전혀 없다(`QTranslator`, `QSettings`, `QLocale`, `gettext` 사용 없음).

## 제안과 가정

아래는 제안이다. 사용자가 승인하지 않았다.

### 진행 순서 (A 방식, 단계마다 PR 하나)

| 단계 | 내용 | 화면 변화 | 버전 | 규모 |
|---|---|---|---|---|
| 1 | 기반 만들기 | Qt 기본 버튼만 한국어로 | 0.7.1 | 작음 |
| 2 | 작업 프로그램 문구 옮기기 | 없음 | — | 중간 |
| 3 | 편집기 · 공통 화면, 화면 없는 계층의 오류 | 없음 | — | 중간 |
| 4 | 영어 문구와 언어 고르기 | 영어 추가, `도구 → 언어` 메뉴 | 0.8.0 | 중간 |
| 5 | 문서와 배포본 | 영어 설명서 | 0.8.0 그대로 | 작음 |

1~3단계는 화면이 바뀌지 않아 사용자 테스트 중에도 진행할 수 있다. 영어가 실제로 보이는 것은 4단계부터다. 0.8.0 배포본은 4 · 5단계를 모두 병합한 뒤 만든다.

**1단계: 기반 만들기**
- `i18n.py`: 언어 정하기(`set_language`), 문구 꺼내기(`t`). 키가 빠지면 한국어로 대신 보여 주고, 테스트에서는 실패로 처리한다.
- `ko.json` 빈 틀. `pyproject.toml`의 package-data와 PyInstaller 설정(`packaging/quick-imposing.spec`)에 문구 파일 포함.
- Qt 기본 번역 파일 불러오기.
- 테스트: 두 문구 파일의 키가 같은지, 같은 키의 값 자리가 같은지.
- 배포본 시작 점검(`--selftest`)에서 문구 파일을 읽는지 확인. Windows 배포 exe가 문구 파일과 Qt 번역 파일을 찾는지 확인.
- 화면 변화: 대화상자 기본 버튼이 한국어가 된다. 미리 알린다.

**2단계: 작업 프로그램 문구 옮기기**
- 옮기기 전에 `work.py`의 한국어 문구를 모두 뽑아 기준 목록을 만든다.
- `ko.json`으로 옮긴다. `ERROR_TEXT` 표와 `describe_error()`도 같은 방식으로.
- 완료 기준: `ko.json`이 기준 목록을 글자 하나까지 재현한다. `work.py`에 한국어 문구가 남아 있으면 실패하는 검사 테스트. 기존 테스트가 그대로 통과한다.

**3단계: 편집기 · 공통 화면, 화면 없는 계층의 오류**
- `editor.py`, `common.py` 문구를 2단계와 같은 방법으로 옮긴다.
- `session.py`, `store.py`의 오류를 코드와 값으로 바꾼다. 예: `SessionError("DIFFERENT_DRIVE")`, `TemplateError("TEMPLATE_NOT_FOUND", name=...)`. 화면이 `t()`로 문장을 만든다.
- 리팩토링 R8(`docs/REFACTORING.md`, 창 클래스에서 판단 로직 분리)과 방향이 같다. 이번에는 오류 문구만 다루고 나머지는 R8로 남긴다.
- 완료 기준: `imposing/` 코드에 사용자에게 보이는 한국어 문구가 없다(주석 · docstring 제외). 화면은 그대로다.

**4단계: 영어 문구와 언어 고르기 (0.8.0)**
- 용어집을 먼저 정하고 검토받는다. 초안: 판 = sheet, 셀 = cell, 데이터 = card/data, 베이스 = base, 하리 = side guide, 임포지션 = imposition.
- `en.json` 채우기.
- 처음 켰을 때 OS 언어가 한국어면 한국어, 그 밖에는 영어. `도구 → 언어`로 바꾸고, 바꾸면 "다시 시작하면 적용됩니다"라고 안내. 고른 언어는 PC에 저장하고 두 프로그램이 같이 쓴다.
- 두 언어로 주요 화면과 대화상자를 캡처해 검토받는다. 영어 문구가 길어 잘리는 곳은 배치를 고친다. 작업 프로그램 왼쪽 칸 폭을 특히 본다.
- Windows: 영어 설정으로 배포본 시작 점검 통과.

**5단계: 문서와 배포본**
- README를 언어별로 나눈다(아래 결정에 따라).
- `build.ps1`이 `사용설명서.md`와 `User-Guide.md`를 둘 다 만든다. 두 README 모두에 같은 자르는 표시(`<!-- 여기부터는 … -->` 또는 영어판의 대응 표시)를 둔다.
- `packaging/collect_licenses.py`가 만드는 `THIRD-PARTY-LICENSES\README.md`를 두 언어로 병기.

### 위험과 대책

| 위험 | 대책 |
|---|---|
| 옮기는 중 한국어 문구가 실수로 바뀜 | 2단계의 기준 목록과 재현 테스트 |
| 한국어 조사와 영어 어순 · 복수형 차이 | 문장 전체를 값 자리가 있는 틀로 만들고 언어마다 따로 쓴다 |
| 영어 문구가 길어 화면이 잘림 | 4단계에서 두 언어 화면 캡처로 확인 |
| 배포본에 문구 파일 · Qt 번역 파일이 빠짐 | 1단계에서 시작 점검과 Windows 워크플로로 확인 |
| 번역 파일 크기 | 수십 KB 수준이라 영향 없음 |

## 열린 질문과 막힌 것

정할 것과 시점:

| 시점 | 정할 것 | 제안 |
|---|---|---|
| 1단계 전 | 처음 켰을 때의 언어, 언어를 바꾸는 방법 | OS 언어를 따르고 `도구 → 언어` 메뉴로 바꾸기, 다시 시작하면 적용 |
| 4단계 전 | 영어 용어집 | 위 초안을 검토 |
| 5단계 전 | README 기본 언어, 배포본 설명서 파일 이름 | 영어 `README.md` + 한국어 `README.ko.md`, 배포본에 `User-Guide.md` 추가 |

확인하지 못한 것:
- Windows 배포본에 Qt 번역 파일이 자동으로 들어가는지(1단계에서 확인).
- PySide6 Windows용 패키지에도 `lupdate` · `lrelease`가 있는지. A 방식에서는 필요 없다.

막힌 것: 없음. 시작 시점만 정해지면 된다.

## 다음 행동

다국어 작업을 다시 시작할 때 이 순서로 한다. 아래는 승인된 작업이 아니라 순서 제안이며, 단계마다 사용자 지시를 받는다.

1. main의 최신 상태를 받고, 그 사이 추가된 기능의 화면 문구도 대상에 넣는다. 이 문서의 수치는 `0df808c` 기준이라 다시 센다.
2. 1단계 전 결정(처음 언어, 바꾸는 방법)을 사용자에게 확인한다.
3. 1단계부터 차례로 진행한다. 단계마다 GitHub PR 설명에 기록, Windows 워크플로 통과, 사용자 지시 후 병합.
4. 4단계 전 용어집, 5단계 전 README 기본 언어를 확인한다.

다국어 작업 전에 기능을 추가할 때 지킬 것(나중 작업을 줄이기 위해, 제안):
- 새 화면 문구는 한 곳에 모아 두거나 상수로 빼 둔다.
- 화면 없는 계층에서 새로 한국어 문장을 만들지 않고, 오류 코드와 값을 넘긴다(R1 · R5와 같은 방식).
- 조사를 붙이는 f-string(`을(를)` 등)을 새로 만들지 않는다.
